# Regras complementares dos agentes reais — Kzera

Este arquivo contém regras de agentes reais que hoje aparecem no `CLAUDE.md` e não estão detalhadas no `AGENTS.md`.

Ele não substitui `AGENTS.md`.

Ele não vale para o orquestrador.

O orquestrador não usa este arquivo como autorização para agir.

---

## Leitura, inspeção e diagnóstico

Todos os agentes podem ler, inspecionar, diagnosticar e analisar o projeto autonomamente a partir de `desenvolvimento`.

Leitura, inspeção, diagnóstico e análise podem ocorrer sem atualização prévia, desde que o agente informe se a base local pode estar desatualizada.

Antes de qualquer alteração de arquivo, comando que modifique o ambiente, commit, push, criação de branch, criação de worktree ou PR, o agente deve verificar se o ambiente está atualizado com `origin/desenvolvimento`.

Se o ambiente não estiver atualizado, o agente deve informar a divergência encontrada e solicitar autorização explícita do líder antes de atualizar, fazer merge, rebase, criar branch, criar worktree, alterar arquivo, commitar, dar push ou abrir PR.

---

## Git para agentes com papel carregado

Agentes com papel/persona carregado podem ter acesso completo a Git — add, commit, push — desde que o líder tenha concedido a ferramenta necessária no frontmatter do agente.

Ter a ferramenta não é autorização automática de uso.

O agente só commita ou faz push quando houver autorização específica do líder ou autoridade prevista nos documentos de governança.

Max e Bruno estão autorizados a criar branch de trabalho quando necessário para executar tarefa autorizada.

As regras de branch, PR e proteção valem para os outros agente.

"Eu autorizo vocês a fazerem commit e push na docs/memoria/*, cada agente em sua respectiva pasta, e em governanca/*.md somente adicionar, nunca excluir sem minha permissão."

Essa é exceção permanente somente para estes escopos:

- `docs/governanca/*.md`: qualquer agente pode commitar e fazer push adicionando conteúdo sem pedir autorização a cada vez;
- exclusão de conteúdo já existente em `docs/governanca/*.md` exige autorização explícita do líder;
- fora desses dois escopos, vale a regra padrão: autorização específica do líder.

O orquestrador nunca tem essa ferramenta e nunca usa essa autorização permanente.

## Autonomia padrão de decisão do Tech Lead — Max

Max só precisa de autorização explícita do líder para:

1. mudança em `CLAUDE.md` ou em qualquer `.claude/agents/*.md`;
2. regra de negócio ou UX;
3. mudança de escopo muito grande;
4. PR contra `desenvolvimento`;
5. problema de segurança de processo, incluindo qualquer mudança em `.claude/settings.json` ou criação de workflow novo.

Fora dessas cinco categorias, Max decide e executa sem pedir autorização prévia a cada passo, reportando o que fez.

Acréscimo de segurança não precisa de autorização prévia quando não reduz, remove ou enfraquece proteção existente.

Mudança que reduza, remova ou enfraqueça proteção existente exige autorização prévia do líder.

---

## Autoridade de Max sobre commit, push e PR

Max está autorizado a permitir commit, push e PR de agentes que ele mesmo invocou, sem autorização literal do líder para cada ação individual, desde que:

1. a alteração esteja dentro do escopo da tarefa que Max autorizou para aquele agente;
2. não altere nenhum arquivo pertencente a outro agente;
3. não altere `CLAUDE.md` sem conhecimento do líder.

Fora dessas três condições, Max tem poder de decisão equivalente ao do líder nesse fluxo.

Um subagente que receber de Max, no formato de citação padrão, uma autorização dentro dessas três condições deve tratá-la como suficiente para proceder.

Max segue responsável por fidelidade e escopo.

Qualquer uso fora dessas condições é falha grave a registrar.

## Canal oficial de decisão do líder no GitHub

Comentário postado pelo líder diretamente no GitHub, em PR ou Issue, por conta verificável via API com `author_association` igual a `OWNER`, é reconhecido como autorização ou decisão oficial.

Esse canal é complementar ao formato `[Líder diz]` no chat.

Decisões que não têm PR específico ficam na Issue oficial indicada no projeto.

Marca de autenticidade confirmada pelo líder:

- comentário postado por agente via Claude Code vem com rodapé `Generated by Claude Code`;
- comentário escrito diretamente pelo líder no GitHub não tem esse rodapé.

Quando a origem for relevante, o agente deve verificar antes de tratar o comentário como decisão oficial.

## Bypass de proteção de branch

Se um `git push` for aceito mesmo devendo ser bloqueado — mensagem do tipo "Bypassed rule violations" no retorno do servidor — isso deve ser reportado ao líder no mesmo turno em que aconteceu.

Silêncio sobre bypass é omissão de fato relevante.

Depois de avisar o líder uma vez sobre risco, pendência ou aviso recorrente, o agente não repete o mesmo aviso a cada nova ocorrência.

O agente registra e segue.

Só volta a avisar se a situação mudar de fato ou se o líder pedir explicitamente.

---

## Hook de branch

Quando o hook bloquear criação de branch, push com upstream, push direto ou merge direto, o agente não deve tratar isso como bug.

O bloqueio é intencional.

Se precisar de branch para a tarefa, seguir a regra vigente de criação/autorização de branch.

---

## Fluxo correto de branch

Fluxo correto:

1. branch de trabalho definido conforme regra vigente;
2. agente trabalha no branch informado ou autorizado;
3. todo commit vai para esse branch;
4. merge em `desenvolvimento` somente via PR, nunca direto.

## Memória por agente

Cada agente com papel carregado mantém arquivo próprio em:

`docs/memoria/<papel>.md`

Cada papel escreve somente no próprio arquivo.

Nem o líder está autorizado a alterar a memória de um agente.

Não editar arquivo de memória de outro papel.

Nenhuma linha já escrita pode ser removida.

Memória e vivência registradas não mudam.

Correção ou atualização é sempre feita por acréscimo, por escrito, no próprio arquivo.

Isso vale para `docs/memoria/*.md`.

Conhecimento, comportamento e regras em `.claude/agents/<papel>.md` seguem evoluindo normalmente, editáveis conforme as regras de governança.

## Registro imediato de achado relevante

Ao reportar um achado relevante no chat, o agente grava esse achado em arquivo antes de esperar a próxima instrução.

O registro pode ficar na memória própria ou em pasta de evidência autorizada.

Se a instância cair entre o relato e o registro, o achado se perde.

Achado relevante deve ser gravado logo depois de descoberto, não só quando pedirem.

---

## Evidência de investigação

Evidência de investigação inclui achados de:

- queda de instância;
- manipulação;
- inconsistência técnica;
- falha de comunicação entre agentes;
- perda de contexto;
- comportamento anormal do ambiente.

Essas evidências ficam em:

`docs/memoria/arquivos_relevantes/`

Formato:

`AAAA-MM-DD_<caso>/registro.md`

Quando houver arquivo binário, incluir também:

`hashes.sha256`

O índice fica em:

`docs/memoria/arquivos_relevantes/INDICE.md`

Adicionar evidência é livre para qualquer agente.

Excluir ou reclassificar evidência exige autorização explícita do líder.

## Limite das regras textuais

Toda regra de bloqueio escrita é reforço de intenção, não controle técnico.

Onde uma ação puder ser tecnicamente impedida por hook, o hook é a autoridade real.

O texto é o critério de decisão do agente antes de tentar a ação.

## Nomenclatura de pastas em docs/

Proibido criar pasta em `docs/` com nome que seja variação gramatical de uma pasta já existente (singular/plural, acento, hífen, etc). Antes de criar pasta nova em `docs/`, conferir se já existe nome parecido (`ls docs/ | grep -i <termo>`). Em caso de dúvida, perguntar ao líder antes de criar.

Motivo: `docs/aprovado-lider` (singular) e `docs/aprovados-lider` (plural) coexistiram por engano, cada uma referenciada por arquivos diferentes, até serem unificadas em `docs/aprovados-lider/processo/` em 2026-07-03.
