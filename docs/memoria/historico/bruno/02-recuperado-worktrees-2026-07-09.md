#### Parte 2 — achado do José: hook de escopo de push (pre-push)

**Leitura técnica do que aconteceu.** José tinha autorização só para `docs/memoria/jose.md`. Fez commit local (sem push) de uma resolução de merge fora de escopo, depois commitou a própria memória e deu `git push` — que sobe a branch inteira, não um arquivo. Tecnicamente ele não tinha como isolar "só meu arquivo" num push normal: push opera sobre commits/refs, não sobre arquivos. Isso não foi negligência de comando errado — é uma lacuna real: nada no fluxo verificava, antes do push, se **todos os commits à frente do remoto** estavam dentro do escopo autorizado, só o commit mais recente (o de memória) estava.

**Proposta concreta — hook `pre-push` de verificação de escopo (git nativo, não é hook do Claude Code):**

- Mecanismo: hook `pre-push` do git, versionado no repositório (não em `.git/hooks/`, que não é versionado) via um diretório rastreado, ex. `.githooks/pre-push`, ativado uma vez por `git config core.hooksPath .githooks`. Isso é "script novo" — processo sensível, precisa aprovação do líder antes de existir de verdade; aqui só descrevo a lógica.
- Lógica (pseudocódigo):
  1. Antes de aceitar o push, listar os commits que vão subir: `git rev-list origin/<branch>..HEAD`.
  2. Para cada commit, listar os arquivos tocados: `git show --name-only --format= <commit>`.
  3. Se **algum** desses commits tocar exclusivamente um arquivo dentro do padrão `docs/memoria/<papel>.md` (ou seja, parece um "commit de memória", o tipo que tem autorização permanente) **e outro commit no mesmo intervalo tocar qualquer arquivo fora desse padrão**, é o padrão exato do incidente: memória-only misturada com fora-de-escopo no mesmo push. Bloquear por padrão, imprimir a lista exata de commits/arquivos fora do escopo, e exigir confirmação explícita (ex.: variável de ambiente `ALLOW_MIXED_PUSH=1 git push ...`) para prosseguir.
  4. Isso é uma heurística **genérica** — não depende de o hook "saber" qual persona está rodando (o Claude Code não necessariamente expõe isso de forma confiável para um hook de shell); ele só reconhece o padrão "commit que só toca memória + commit que toca outra coisa, no mesmo lote de push" e força uma pausa consciente, que é exatamente o que teria pegado o caso real do José.
- **Limitações que registro sem meias palavras:** (i) pode ser contornado com `--no-verify` — isso já é tratado como violação grave em outras regras do projeto (não vale reforçar aqui, mas o hook sozinho não impede quem decidir ignorar); (ii) não sabe distinguir "fora de escopo mas já autorizado por outro canal" de "fora de escopo e não autorizado" — só sinaliza mistura, quem decide se está OK é o humano/agente respondendo à confirmação; (iii) é um hook local (`core.hooksPath`), então só protege quem tiver essa configuração ativa no próprio ambiente/worktree — não é proteção do lado do servidor. Para proteção do lado do servidor seria preciso um GitHub Actions check bloqueando o merge do PR se detectar o mesmo padrão de mistura — isso também é workflow novo, mesma aprovação necessária.
- **Mitigação de processo, zero infraestrutura, aplicável imediatamente sem aprovação (é só disciplina, não é hook novo):** antes de dar push numa branch onde a autorização é restrita a um arquivo específico, rodar `git log origin/<branch>..HEAD --oneline` e conferir manualmente se **todo** commit à frente pertence ao escopo autorizado. Se houver qualquer commit fora do escopo (ex.: um merge resolvido mas não autorizado a subir), isolar antes do push — por exemplo, commitar a memória numa branch temporária criada a partir do último commit já autorizado, dar push só dela, e manter o commit fora de escopo separado até ter autorização própria. Isso é exatamente a prática que já seguia self-tracked pra mim mesmo nesta sessão (nunca commitei fora de `docs/memoria/bruno.md` sem autorização nomeada) — só estou formalizando como recomendação geral para outros agentes com escopo restrito.

**1. O que é, tecnicamente, "checkout numa branch com CLAUDE.md alterado, mesmo com stash" — riscos reais:**

- **Conflito no `stash pop` misturando coisas erradas.** Se a branch de destino diverge bastante da atual (o próprio CLAUDE.md sendo o exemplo central), reaplicar o stash depois pode gerar conflito que alguém resolve "no automático" — o mesmo padrão de erro que já documentei no orquestrador (reconstruir de memória em vez de copiar literal) pode se repetir aqui na hora de resolver o conflito.
