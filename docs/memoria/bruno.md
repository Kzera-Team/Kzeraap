#### Parte 2 — Opinião técnica: como reduzir o risco do erro do José (push de branch inteira arrastando commit não autorizado)

Reconstrução do caso, a partir de `docs/memoria/max.md` (2026-07-05, "PR #104: José pushou em `n1` sem autorização"): José tinha autorização de commit/push restrita a `docs/memoria/jose.md`. Havia, na mesma branch, um commit de merge (`d917627`) já feito localmente mas **não pushado ainda** (Max pediu explicitamente para não dar push, só trazer o diff). Ao José commitar sua entrada de memória e rodar `git push`, o Git subiu a branch inteira — o commit de merge (não autorizado a subir ainda) foi junto, porque `git push` sobe todos os commits novos do ref, não um arquivo isolado. Causa raiz dupla: (a) mecânica do Git (push é por ref/branch, não por arquivo) colidindo com um modelo mental de "autorização por arquivo"; (b) ausência de `isolation: worktree` fez o José rodar no mesmo diretório de trabalho que o Max, mas isso explica por que o Max *percebeu* o problema (`HEAD` mudando por baixo dele), não é a causa do push em si — o push foi decisão/ação do próprio José, rodando sozinho, teria acontecido do mesmo jeito mesmo isolado.

Camadas de mitigação, da mais barata/imediata para a mais estrutural:

1. **Regra absoluta, sem exceção, adotável hoje sem ferramenta nova:** enquanto existir uma instrução ativa de "não faça push" para uma branch (de quem quer que seja — Max, líder, outro agente), nenhum agente roda `git push` **para essa branch**, nem mesmo para um arquivo dentro do próprio escopo autorizado. Autorização por arquivo nunca é maior que uma instrução de "segura o push" na mesma branch, porque tecnicamente não existe "push só desse arquivo" — quem autoriza por arquivo está autorizando o *conteúdo*, não o ato de subir a branch inteira no momento que for. Isso sozinho já teria evitado o caso do José.
2. **Checagem mecânica antes de qualquer push com autorização restrita a arquivo(s):** antes de `git push`, rodar `git log @{u}..HEAD --name-only` (ou equivalente comparando contra o remoto real) e conferir que **todos** os commits no intervalo tocam só o(s) caminho(s) autorizado(s). Se houver mais de um commit no intervalo, ou qualquer commit tocando arquivo fora do escopo, parar e escalar em vez de empurrar. Isso é literalmente o teste que teria pego o caso do José (o commit de merge, tocando `CLAUDE.md`/`.claude/agents/jose.md`/`.claude/settings.json`, apareceria no `--name-only` antes do push). Posso formalizar isso como recomendação de processo no CLAUDE.md (proposta, não edito sozinho) ou como um script utilitário simples em `scripts/` que qualquer agente pode rodar antes de decidir empurrar — ficaria disponível sem mexer em `.claude/settings.json`/hooks (isso seria categoria 5, exige autorização prévia do líder).
3. **`isolation: worktree` obrigatório para qualquer subagente cuja tarefa envolva `git checkout`/commit/push** — não evita o erro do José por si só (ver acima), mas evita a classe de bug irmã (estado git compartilhado mudando por baixo de outro processo, como aconteceu comigo agora mesmo nesta própria tarefa, ver "achado ao vivo" acima, e já duas vezes antes com Max/José). Ponto de governança já identificado por Max e ainda pendente: o CLAUDE.md diz que nenhum agente cria worktree isolado sem autorização explícita do líder "para aquela tarefa específica"; o líder já respondeu que isso é "configuração de competência do orquestrador" — ou seja, não é decisão que eu ou outro agente tome sozinho caso a caso; é o orquestrador quem administra isso, cabe a ele detalhar como ativar/desativar. Não decido nem aplico nada aqui, só reforço que a mitigação técnica correta existe e já foi identificada.
