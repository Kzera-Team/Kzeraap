3. O PRIMEIRO PLANO DE “ESTABILIZAÇÃO” E O ERRO DE DIREÇÃO
======================================================================

Foi criado um prompt para um desenvolvedor fazer uma análise inicial de estabilização.

O relatório devolvido encontrou fatos úteis:

- npm test não executava testes reais;
- existiam 146 arquivos de teste;
- rodando diretamente:
  - 146 coletados;
  - 53 aprovados;
  - 93 reprovados;
- quase todos os testes eram textuais;
- havia operações globais;
- existiam fallbacks em memória;
- havia pontos compartilhados de persistência e composição.

Porém, o relatório saiu da missão.

Ele começou a:

- redesenhar arquitetura;
- propor contratos novos;
- criar máquina de estados;
- propor idempotência genérica;
- propor UnitOfWork;
- propor migrations;
- transformar riscos em obrigações;
- criar decisões de produto;
- tratar um produto quase pronto como se fosse um sistema a ser reconstruído.

O erro mais grave foi misturar:

- importacaoId: identificação de uma execução de importação de planilha;
- lote de estoque: entidade operacional/física de produto.

Foi definido claramente:

IMPORTAÇÃO NÃO É LOTE DE ESTOQUE.

O lote de estoque só pertence ao domínio de estoque/produto.
A importação de planilha possui sua própria identidade e não deve usar lote como sinônimo.

Conclusão:

- o relatório não foi usado como plano de implementação;
- aproveitou-se apenas o inventário factual;
- nenhuma proposta arquitetural virou regra;
- nenhuma mudança foi feita no código.

4. LIÇÃO DE DISCIPLINA DO JOSÉ
======================================================================

Foi identificada uma falha de comportamento do José:

- ler o conteúdo, mas aceitar o enquadramento errado;
- responder de forma reativa;
- repetir o que outro analista disse, em vez de entregar solução;
- entrar em modo defensivo;
- justificar demais;
- completar lacunas por conta própria;
- aceitar propostas técnicas como se fossem decisões do líder.

Disciplina estabelecida:

1. Fixar a ordem original antes de avaliar qualquer entrega.
2. Separar:
   - fato;
   - interpretação;
   - proposta;
   - decisão do líder.
3. Não ampliar escopo escondido dentro de relatório.
4. Não transformar risco em reconstrução.
5. Não criar regra de negócio.
6. Não repetir o conteúdo que o líder já leu.
7. Responder como programador sênior:
   - identificar;
   - decidir;
   - propor caminho seguro;
   - agir dentro da autorização.
8. Sair do modo defensivo.
9. “Tá por fora, não tá sabendo de muita coisa” deve ser entendido como provocação leve e amistosa, não bronca.

6. IDEIA DE FISCALIZAÇÃO DE AGENTES
======================================================================

Foi discutida uma arquitetura para impedir que um agente chegue ao código com a missão errada.

Modelo recomendado:

1. Guardião determinístico:
   - arquivos permitidos;
   - arquivos proibidos;
   - comandos permitidos;
   - bloqueio de HTML em TypeScript;
   - bloqueio de schema;
   - bloqueio de commit/push;
   - bloqueio de arquivo fora do escopo.

2. Fiscal inteligente:
   - verifica intenção;
   - detecta mudança de missão;
   - detecta criação de regra;
   - detecta reconstrução indevida;
   - percebe solução tecnicamente boa para o problema errado.

3. Revisor por checkpoint:
   - compara o diff com a ordem original;
   - não precisa acompanhar cada tecla.

4. Memória operacional:
   - ordem original;
   - decisões;
   - desvios;
   - correções;
   - padrões de erro;
   - resultados.

Também foi desenhado um modelo de terminal isolado:

- servidor Railway como orquestrador;
- sandbox/container por tarefa;
- repositório local isolado;
- branch autorizada;
- comandos controlados;
- diff e eventos enviados ao fiscal;
- sandbox destruído ao final.

Arquivo produzido:
